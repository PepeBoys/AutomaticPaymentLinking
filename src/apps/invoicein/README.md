# Приложение invoicein - Работа со счетами поставщиков

## Описание

Модуль `invoicein` реализует работу со счетами поставщиков (supplier invoices) МойСклад. Приложение построено на базе `payable_document_base` и переиспользует функциональность через наследование. Счета поставщиков используются для учета выставленных поставщиками счетов и привязки исходящих платежей.

**Важно**: Это **внутренний модуль** без REST API endpoints. Используется только через `WebhookHandler` для автоматической привязки исходящих платежей (paymentout, cashout) к счетам поставщиков.

## Основные компоненты

### 1. Доменная модель
```
┌────────────────────────────────────────────────────────────────┐
│              BasePayableDocumentEntity                         │
│              (from payable_document_base)                      │
├────────────────────────────────────────────────────────────────┤
│  + id: str                                                     │
│  + account_id: str                                             │
│  + name: str                                                   │
│  + moment: datetime                                            │
│  + applicable: bool                                            │
│  + sum: float                                                  │
│  + payed_sum: float                    ← Оплачено              │
│  + shipped_sum: float | None           ← Может использоваться  │
│  + invoiced_sum: float | None          ← НЕ используется       │
│  + agent_id: str                       ← Поставщик!            │
│  + organization_id: str                                        │
│  + meta_href: str                                              │
│  + project_meta_href: str | None                               │
│  + sales_channel_meta_href: str | None                         │
├────────────────────────────────────────────────────────────────┤
│  + get_unpaid_amount() -> float                                │
│      Вычислить неоплаченную сумму (sum - payed_sum)            │
│  + is_fully_paid() -> bool                                     │
│      Проверить, полностью ли оплачен счет                      │
└────────────────────────────────────────────────────────────────┘
                        △
                        │
                        │ extends (без изменений)
                        │
┌────────────────────────────────────────────────────────────────┐
│                   InvoiceInEntity                              │
├────────────────────────────────────────────────────────────────┤
│  (все поля наследуются от базового класса)                     │
│  (нет дополнительных полей или методов)                        │
│                                                                │
│  ПРИМЕЧАНИЕ:                                                   │
│  • agent_id - это ПОСТАВЩИК (supplier), не покупатель          │
│  • shipped_sum может использоваться (если есть приемка)        │
│  • invoiced_sum всегда None (счет УЖЕ выставлен)               │
└────────────────────────────────────────────────────────────────┘
```

## Примеры использования

### Использование из WebhookHandler
```python
# Поиск счетов поставщика для привязки исходящего платежа
invoices = await invoicein_service.find_for_payment(
    agent_id="supplier_456",  # ← Поставщик, не покупатель!
    payment_sum=50000.0,
    search_by_sum=True,
    organization_id="org_789",
    prioritize_oldest=True
)

# Привязка исходящего платежа к счету поставщика
await paymentout_service.link_to_document(
    payment_id="paymentout_123",
    document_meta_href="entity/invoicein/invoice_456",
    linked_sum=50000.0
)

# Обновление статуса счета
await invoicein_service.update_state(
    document_id="invoice_123",
    state_id="state_paid"
)

# Поиск счета по номеру и поставщику
invoice = await invoicein_service.find_by_name_and_agent(
    name="SF-00042",
    agent_id="supplier_456",
    organization_id="org_789"
)

# Получение счета по href
invoice = await invoicein_service.get_by_href(
    "https://api.moysklad.ru/api/remap/1.2/entity/invoicein/invoice_123"
)
```

### Работа с доменными методами
```python
# Получить счет поставщика
invoice = await invoicein_service.get_by_id("invoice_123")

# Проверить статус оплаты
unpaid_amount = invoice.get_unpaid_amount()  # sum - payed_sum
is_paid = invoice.is_fully_paid()            # payed_sum >= sum

# Информация о счете
print(f"Счет {invoice.name} от поставщика")
print(f"Сумма: {invoice.sum}")
print(f"Оплачено: {invoice.payed_sum}")
print(f"Осталось оплатить: {unpaid_amount}")
```

## Интеграция с системой webhook
```

│              РОЛЬ В АВТОМАТИЧЕСКОЙ ПРИВЯЗКЕ                    │

WebhookHandler при обработке ИСХОДЯЩИХ платежей:

1. Получает платеж (paymentout/cashout) через PaymentService
2. Ищет подходящие документы (purchaseorder, invoicein, supply)
3. Приоритизирует документы (заказы → счета → приемки)
4. Привязывает платеж к найденным документам
5. Применяет статусы (опционально)

┌─────────────────────────────────────────────────────────────────┐
│                                                                 │
│  МойСклад → Webhook → WebhookService → WebhookHandler           │
│                                               │                 │

```

## Различия между типами счетов
```
╔═══════════════════════════════════════════════════════════════════╗
║              INVOICEOUT vs INVOICEIN                              ║
╠═══════════════════════════════════════════════════════════════════╣
║                                                                   ║
║  ┌──────────────┬─────────────┬─────────────┬──────────────┐      ║
║  │ Документ     │ Направление │ Контрагент  │ Платежи      │      ║
║  ├──────────────┼─────────────┼─────────────┼──────────────┤      ║
║  │ invoiceout   │ Продажа     │ Покупатель  │ Входящие     │      ║
║  │              │ (Outgoing)  │ (customer)  │ paymentin    │      ║
║  │              │             │             │ cashin       │      ║
║  │              │             │             │              │      ║
║  │ invoicein    │ Покупка     │ Поставщик   │ Исходящие    │      ║
║  │              │ (Incoming)  │ (supplier)  │ paymentout   │      ║
║  │              │             │             │ cashout      │      ║
║  └──────────────┴─────────────┴─────────────┴──────────────┘      ║
║                                                                   ║
║  ВНИМАНИЕ: Naming Convention!                                     ║
║  • invoiceout = счет ИСХОДЯЩИЙ (from us to customer)              ║
║  • invoicein  = счет ВХОДЯЩИЙ (from supplier to us)               ║
║                                                                   ║
║  Это может быть неинтуитивно, но:                                 ║
║  • "out" = мы ВЫСТАВИЛИ счет покупателю                           ║
║  • "in"  = нам ВЫСТАВИЛИ счет поставщики                          ║
║                                                                   ║
╚═══════════════════════════════════════════════════════════════════╝
```

## Приоритет документов для исходящих платежей
```
╔═══════════════════════════════════════════════════════════════════╗
║       PURCHASEORDER vs INVOICEIN vs SUPPLY                        ║
╠═══════════════════════════════════════════════════════════════════╣
║                                                                   ║
║  ┌──────────────────┬──────────┬────────────┬──────────────┐      ║
║  │ Документ         │ Тип      │ Shipped    │ Invoiced     │      ║
║  ├──────────────────┼──────────┼────────────┼──────────────┤      ║
║  │ purchaseorder    │ Заказ    │ ✓ Есть     │ ✓ Есть      │      ║
║  │ invoicein        │ Счет     │ ✓ Может    │ ✗ Нет       │      ║
║  │ supply           │ Приемка  │ ✗ Нет      │ ✗ Нет       │      ║
║  └──────────────────┴──────────┴────────────┴──────────────┘      ║
║                                                                   ║
║  ПРИОРИТЕТ ПРИВЯЗКИ ИСХОДЯЩИХ ПЛАТЕЖЕЙ:                           ║
║  1. purchaseorder  → Заказ поставщику (основной документ)         ║
║  2. invoicein      → Счет от поставщика (выставлен счет)          ║
║  3. supply         → Приемка (товар уже принят)                   ║
║                                                                   ║
║  ОБЩИЕ ПОЛЯ:                                                      ║
║  • sum           → Общая сумма документа                          ║
║  • payed_sum     → Оплачено по документу                          ║
║  • agent_id      → Контрагент (ПОСТАВЩИК!)                        ║
║  • organization_id → Организация (ПОКУПАТЕЛЬ!)                    ║
║                                                                   ║
║  МЕТОДЫ:                                                          ║
║  • get_unpaid_amount() → sum - payed_sum                          ║
║  • is_fully_paid()     → payed_sum >= sum                         ║
║                                                                   ║
╚═══════════════════════════════════════════════════════════════════╝
```

## Особенности реализации
```
╔═══════════════════════════════════════════════════════════════════╗
║                    КЛЮЧЕВЫЕ ОСОБЕННОСТИ                           ║
╠═══════════════════════════════════════════════════════════════════╣

║  1. ВНУТРЕННИЙ МОДУЛЬ БЕЗ REST API                                ║

║     InvoiceIn используется для привязки:                          ║
║     • paymentout (исходящие платежи)                              ║
║     • cashout (расходные ордера)                                  ║
║     К счетам ОТ поставщиков                                       ║
║                                                                   ║
║  3. NAMING CONVENTION                                             ║
║     Может быть неинтуитивно:                                      ║
║     • invoicein  = счет ВХОДЯЩИЙ (к нам от поставщика)            ║
║     • invoiceout = счет ИСХОДЯЩИЙ (от нас к покупателю)           ║
║     "In/Out" с точки зрения ДОКУМЕНТА, не денег!                  ║
║                                                                   ║
║  4. МИНИМАЛЬНЫЙ КОД                                               ║
║     Файл                         Строк кода                       ║
║     ──────────────────────────   ─────────                        ║
║     dependencies.py                 17                            ║
║     domain/entities.py               8                            ║
║     exceptions.py                    9                            ║
║     exception_handlers.py           12                            ║
║     schemas.py                       6                            ║
║     services/invoicein_client.py     8                            ║
║     services/invoicein_service.py   60                            ║
║     ────────────────────────────────                              ║
║     ИТОГО:                         ~120 строк                     ║
║                                                                   ║
║  5. НЕТ VALUE OBJECTS                                             ║
║     • Нет InvoiceInFilter (не нужен)                              ║
║     • Фильтрация через базовый класс                              ║
║     • Упрощение правильное для внутреннего модуля                 ║
║                                                                   ║
║  6. ВАЛИДАЦИЯ В _TO_ENTITY                                        ║
║     ```python                                                     ║
║     if not data.get("meta", {}).get("href"):                      ║
║         raise InvoiceInNotFoundError(...)                         ║
║     ```                                                           ║
║     Проверка обязательных полей при парсинге                      ║
║                                                                   ║
║  7. SHIPPED_SUM МОЖЕТ ИСПОЛЬЗОВАТЬСЯ                              ║
║     Если есть связанная приемка (supply):                         ║
║     • shipped_sum: Показывает принятое количество                 ║
║     • invoiced_sum: Нет смысла (счет УЖЕ выставлен)               ║
║                                                                   ║
╚═══════════════════════════════════════════════════════════════════╝
```

## Архитектурное решение: внутренний модуль
```
╔═══════════════════════════════════════════════════════════════════╗
║              ПОЧЕМУ НЕТ REST API ENDPOINTS?                       ║
╠═══════════════════════════════════════════════════════════════════╣
║                                                                   ║
║  ПРИЧИНЫ ДИЗАЙН-РЕШЕНИЯ:                                          ║
║                                                                   ║
║  1. Счета поставщиков используются ТОЛЬКО для автоматической      ║
║     привязки ИСХОДЯЩИХ платежей                                   ║
║     • WebhookHandler находит счета                                ║
║     • Никакого ручного управления не требуется                    ║
║     • UI не нужен доступ к счетам поставщиков                     ║
║                                                                   ║
║  2. Приоритет документов (заказы важнее счетов)                   ║
║     • Сначала ищется purchaseorder                                ║
║     • Потом invoicein                                             ║
║     • В последнюю очередь supply                                  ║
║                                                                   ║
║  3. Упрощение архитектуры                                         ║
║     • Меньше кода для поддержки                                   ║
║     • Меньше attack surface                                       ║
║     • Четкое разделение: public vs internal                       ║
║                                                                   ║
║  4. Симметрия с invoiceout                                        ║
║     • invoiceout (входящие платежи) - internal                    ║
║     • invoicein (исходящие платежи) - internal                    ║
║     • Оба работают одинаково через webhook                        ║
║                                                                   ║
║  КОГДА МОЖЕТ ПОНАДОБИТЬСЯ API:                                    ║
║  • Если нужен UI для просмотра счетов поставщиков                 ║
║  • Если требуется ручная привязка платежей                        ║
║  • Если нужна интеграция с другими системами                      ║
║                                                                   ║
║  В текущей реализации это не требуется, поэтому API нет.          ║
║                                                                   ║
╚═══════════════════════════════════════════════════════════════════╝
```
