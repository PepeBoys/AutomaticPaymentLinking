# Приложение invoiceout - Работа со счетами покупателям

## Описание

Модуль `invoiceout` реализует работу со счетами покупателям (customer invoices) МойСклад. Приложение построено на базе `payable_document_base` и переиспользует функциональность через наследование. Счета покупателям используются для учета выставленных клиентам счетов и привязки входящих платежей.

**Важно**: Это **внутренний модуль** без REST API endpoints. Используется только через `WebhookHandler` для автоматической привязки входящих платежей (paymentin, cashin) к счетам покупателям.

## Основные компоненты

### 1. Доменная модель
```
┌────────────────────────────────────────────────────────────────┐
│              BasePayableDocumentEntity                         │
│              (from payable_document_base)                      │

│  + organization_id: str                                        │

│  + get_unpaid_amount() -> float                                │
│      Вычислить неоплаченную сумму (sum - payed_sum)            │

                        │

├────────────────────────────────────────────────────────────────┤
│  (все поля наследуются от базового класса)                     │

│  ПРИМЕЧАНИЕ:                                                   │
│  • agent_id - это ПОКУПАТЕЛЬ (customer), не поставщик          │

## Примеры использования

### Использование из WebhookHandler
```python
# Поиск счетов покупателю для привязки входящего платежа
invoices = await invoiceout_service.find_for_payment(
    agent_id="customer_456",  # ← Покупатель, не поставщик!
    payment_sum=25000.0,
    search_by_sum=True,
    organization_id="org_789",
    prioritize_oldest=True
)

# Привязка входящего платежа к счету покупателю
await paymentin_service.link_to_document(
    payment_id="paymentin_123",
    document_meta_href="entity/invoiceout/invoice_456",
    linked_sum=25000.0
)

# Обновление статуса счета
await invoiceout_service.update_state(
    document_id="invoice_123",
    state_id="state_paid"
)

# Поиск счета по номеру и покупателю
invoice = await invoiceout_service.find_by_name_and_agent(
    name="INV-00042",
    agent_id="customer_456",
    organization_id="org_789"
)

# Получение счета по href
invoice = await invoiceout_service.get_by_href(
    "https://api.moysklad.ru/api/remap/1.2/entity/invoiceout/invoice_123"
)
```

### Работа с доменными методами
```python
# Получить счет покупателю
invoice = await invoiceout_service.get_by_id("invoice_123")

# Проверить статус оплаты
unpaid_amount = invoice.get_unpaid_amount()  # sum - payed_sum
is_paid = invoice.is_fully_paid()            # payed_sum >= sum

# Информация о счете
print(f"Счет {invoice.name} для покупателя")
print(f"Сумма: {invoice.sum}")
print(f"Оплачено: {invoice.payed_sum}")
print(f"Осталось оплатить: {unpaid_amount}")
```

## Интеграция с системой webhook

WebhookHandler при обработке ВХОДЯЩИХ платежей:

1. Получает платеж (paymentin/cashin) через PaymentService
2. Ищет подходящие документы (customerorder, invoiceout, demand)
3. Приоритизирует документы (заказы → счета → отгрузки)
4. Привязывает платеж к найденным документам
5. Применяет статусы (опционально)

## Различия между типами счетов
```
╔═══════════════════════════════════════════════════════════════════╗
║              INVOICEOUT vs INVOICEIN                              ║
╠═══════════════════════════════════════════════════════════════════╣
║                                                                   ║
║  ┌──────────────┬─────────────┬─────────────┬──────────────┐      ║
║  │ Документ     │ Направление │ Контрагент  │ Платежи      │      ║
║  ├──────────────┼─────────────┼─────────────┼──────────────┤      ║
║  │ invoiceout   │ Продажа     │ Покупатель  │ Входящие     │      ║
║  │              │ (Outgoing)  │ (customer)  │ paymentin    │      ║
║  │              │             │             │ cashin       │      ║
║  │              │             │             │              │      ║
║  │ invoicein    │ Покупка     │ Поставщик   │ Исходящие    │      ║
║  │              │ (Incoming)  │ (supplier)  │ paymentout   │      ║
║  │              │             │             │ cashout      │      ║
║  └──────────────┴─────────────┴─────────────┴──────────────┘      ║
║                                                                   ║
║  ВАЖНО: Naming Convention!                                        ║
║  • invoiceout = счет ИСХОДЯЩИЙ (from us to customer)              ║
║  • invoicein  = счет ВХОДЯЩИЙ (from supplier to us)               ║
║                                                                   ║
║  Это может быть неинтуитивно, но:                                 ║
║  • "out" = мы ВЫСТАВИЛИ счет покупателю                           ║
║  • "in"  = нам ВЫСТАВИЛИ счет поставщики                          ║
║                                                                   ║
╚═══════════════════════════════════════════════════════════════════╝
```

║                                                                   ║
║  ┌──────────────────┬──────────┬────────────┬──────────────┐      ║
║  │ Документ         │ Тип      │ Shipped    │ Invoiced     │      ║

║  │ customerorder    │ Заказ    │ ✓ Есть     │ ✓ Есть      │      ║
║  │ invoiceout       │ Счет     │ ✓ Может    │ ✗ Нет       │      ║
║  │ demand           │ Отгрузка │ ✗ Нет      │ ✗ Нет       │      ║
║  └──────────────────┴──────────┴────────────┴──────────────┘      ║
║                                                                   ║
║  ПРИОРИТЕТ ПРИВЯЗКИ ВХОДЯЩИХ ПЛАТЕЖЕЙ:                            ║
║  1. customerorder  → Заказ покупателя (основной документ)         ║
║  2. invoiceout     → Счет покупателю (выставлен счет)             ║
║  3. demand         → Отгрузка (товар уже отгружен)                ║
║                                                                   ║
║  ОБЩИЕ ПОЛЯ:                                                      ║
║  • sum           → Общая сумма документа                          ║
║  • payed_sum     → Оплачено по документу                          ║

║  • organization_id → Организация (продавец)                       ║
║                                                                   ║
║  МЕТОДЫ:                                                          ║
║  • get_unpaid_amount() → sum - payed_sum                          ║

## Особенности реализации
```
╔═══════════════════════════════════════════════════════════════════╗
║                    КЛЮЧЕВЫЕ ОСОБЕННОСТИ                           ║
╠═══════════════════════════════════════════════════════════════════╣

║     • paymentin (входящие платежи)                                ║
║     • cashin (приходные ордера)                                   ║
║     К счетам ДЛЯ покупателей                                      ║
║                                                                   ║
║  3. NAMING CONVENTION                                             ║
║     Может быть неинтуитивно:                                      ║
║     • invoiceout = счет ИСХОДЯЩИЙ (от нас к покупателю)           ║
║     • invoicein  = счет ВХОДЯЩИЙ (к нам от поставщика)            ║
║     "In/Out" с точки зрения ДОКУМЕНТА, не денег!                  ║
║                                                                   ║
║  4. МИНИМАЛЬНЫЙ КОД                                               ║
║     Файл                         Строк кода                       ║
║     ──────────────────────────   ─────────                        ║
║     dependencies.py                 17                            ║
║     domain/entities.py               8                            ║
║     exceptions.py                    9                            ║
║     exception_handlers.py           12                            ║
║     schemas.py                       6                            ║
║     services/invoiceout_client.py    8                            ║
║     services/invoiceout_service.py  57                            ║
║     ────────────────────────────────                              ║
║     ИТОГО:                         ~117 строк                     ║
║                                                                   ║
║  5. НЕТ VALUE OBJECTS                                             ║
║     • Нет InvoiceOutFilter (не нужен)                             ║
║     • Фильтрация через базовый класс                              ║
║     • Упрощение правильное для внутреннего модуля                 ║
║                                                                   ║
║  6. ВАЛИДАЦИЯ В _TO_ENTITY                                        ║
║     ```python                                                     ║
║     if not data.get("meta", {}).get("href"):                      ║
║         raise InvoiceOutNotFoundError(...)                        ║
║     ```                                                           ║
║     Проверка обязательных полей при парсинге                      ║
║                                                                   ║
║  7. SHIPPED_SUM МОЖЕТ ИСПОЛЬЗОВАТЬСЯ                              ║
║     Если есть связанная отгрузка (demand):                        ║
║     • shipped_sum: Показывает отгруженное количество              ║
║     • invoiced_sum: Нет смысла (счет УЖЕ выставлен)               ║
║                                                                   ║

```

## Архитектурное решение: внутренний модуль
```
╔═══════════════════════════════════════════════════════════════════╗
║              ПОЧЕМУ НЕТ REST API ENDPOINTS?                       ║
╠═══════════════════════════════════════════════════════════════════╣
║                                                                   ║
║  ПРИЧИНЫ ДИЗАЙН-РЕШЕНИЯ:                                          ║
║                                                                   ║
║  1. Счета покупателям используются ТОЛЬКО для автоматической      ║
║     привязки ВХОДЯЩИХ платежей                                    ║
║     • WebhookHandler находит счета                                ║
║     • Никакого ручного управления не требуется                    ║
║     • UI не нужен доступ к счетам покупателям                     ║
║                                                                   ║
║  2. Приоритет документов (заказы важнее счетов)                   ║
║     • Сначала ищется customerorder                                ║
║     • Потом invoiceout                                            ║
║     • В последнюю очередь demand                                  ║
║                                                                   ║
║  3. Упрощение архитектуры                                         ║
║     • Меньше кода для поддержки                                   ║
║     • Меньше attack surface                                       ║
║     • Четкое разделение: public vs internal                       ║
║                                                                   ║
║  4. Симметрия с invoicein                                         ║
║     • invoiceout (входящие платежи) - internal                    ║
║     • invoicein (исходящие платежи) - internal                    ║
║     • Оба работают одинаково через webhook                        ║
║                                                                   ║
║  КОГДА МОЖЕТ ПОНАДОБИТЬСЯ API:                                    ║
║  • Если нужен UI для просмотра счетов покупателям                 ║
║  • Если требуется ручная привязка платежей                        ║
║  • Если нужна интеграция с другими системами                      ║
║                                                                   ║
║  В текущей реализации это не требуется, поэтому API нет.          ║
║                                                                   ║
╚═══════════════════════════════════════════════════════════════════╝
```
